
# ¿Cuál es el esquema general de todos los archivos `.templ` y sus archivos `_templ.go` generados en el proyecto, cómo se estructuran sus componentes y cómo interactúan con los handlers y las rutas de `main.go`?

-- A continuación tenés una explicación completa de cómo funcionan las vistas con **Templ** (`github.com/a-h/templ` v0.3.1100) en este proyecto, qué hace cada archivo y cómo fluyen los datos desde las rutas hasta el HTML final.

---

### 1. ¿Qué son los archivos `.templ` y los `*_templ.go`?

En `views/` vas a encontrar pares de archivos:

| Archivo fuente (editable) | Archivo generado por Templ (NO editar a mano) |
| :--- | :--- |
| `views/layout.templ` | `views/layout_templ.go` |
| `views/usuario.templ` | `views/usuario_templ.go` |
| `views/create_usuario.templ` | `views/create_usuario_templ.go` |

- **Los `.templ`** son plantillas donde mezclás código Go (imports, `if`, `for`, tipos como `[]db.Usuario`) con HTML.
- **Los `*_templ.go`** son archivos Go generados automáticamente por la CLI de `templ` (`templ generate`). Cada bloque `templ Nombre(...)` se compila a una función Go normal en el paquete `views` que devuelve un `templ.Component`.
- **¿Cómo se renderizan?** Desde `handlers/usuario_handler.go`, el servidor simplemente llama a:
  ```go
  views.NombreComponente(args...).Render(r.Context(), w)
  ```
  Esto escribe el HTML directamente en el `http.ResponseWriter` (`w`).
- **Regla clave para la reforma:** Nunca edites los `*_templ.go` directamente (tienen la cabecera `// Code generated by templ - DO NOT EDIT.`). Siempre editás el `.templ` y volvés a correr `templ generate` para regenerar el código Go antes de compilar o ejecutar el servidor.

---

### 2. Esquema general de composición (jerarquía de componentes)

Todas las páginas completas comparten un mismo cascarón HTML llamado **`LayoutBase`**. Las distintas pantallas se "inyectan" dentro de `LayoutBase` mediante `{ children... }`:

```text
LayoutBase(titulo, usuarioActivo)                  [views/layout.templ]
 │   (<!DOCTYPE html>, <head>, CSS, navbar superior)
 │
 ├── LayoutPrincipal(...)                          [views/layout.templ]  <-- GET / y GET /usuarios
 │    └── ListaUsuarios(...)                       [views/usuario.templ]
 │
 ├── CreateUsuarioPage(errorMsg)                   [views/create_usuario.templ] <-- GET /usuarios/nuevo
 │
 ├── LoginPage(emailPrellenado, errorMsg)          [views/usuario.templ] <-- GET /login y POST /login (si hay error)
 │
 └── TP6Aviso(usuarioNombre)                       [views/usuario.templ] <-- GET /tp6, /calendario, /materias
```

---

### 3. Detalle archivo por archivo y componente por componente

#### A. `views/layout.templ` (y `views/layout_templ.go`)

Contiene dos componentes:

1. **`LayoutBase(titulo string, usuarioActivo string)`**
   - Es la plantilla base de toda la aplicación.
   - Define el `<!DOCTYPE html>`, `<html lang="es">` y el `<head>` cargando:
     - Fuentes de Google Fonts (`Caveat` y `Inter`).
     - Íconos de FontAwesome 6.4.0.
     - La hoja de estilos local `/css/style.css` (servida en `main.go` desde `./static/css`).
   - Dibuja la barra de navegación superior (`<header class="site-header">`):
     - Logo `go_tasks` (enlace a `/usuarios`).
     - Un badge de usuario: si `usuarioActivo != ""` muestra el nombre recibido; si está vacío, muestra `"Sin sesión activa"`.
     - Pestañas de navegación (`nav-tabs`): **Usuarios** (`/usuarios`), **Calendario** (`/calendario`) y **Materias** (`/materias`).
   - En `<main class="main-wrapper">` coloca `{ children... }`, que es el espacio donde se inserta el contenido de la página hija.

2. **`LayoutPrincipal(usuarios []db.Usuario, usuarioActivoID int32, usuarioActivoNombre string)`**
   - Es la página principal del sistema.
   - Envuelve su contenido usando `@LayoutBase("go_tasks - Gestión de Usuarios", usuarioActivoNombre)`.
   - Muestra el encabezado de la sección (`go_tasks` + subtítulo `"Seleccionar Usuario para Iniciar Sesión"`).
   - Llama al componente hijo `@ListaUsuarios(usuarios, usuarioActivoID)` (definido en `usuario.templ`).
   - Agrega abajo el botón **"Crear Nuevo Usuario"** que lleva a `/usuarios/nuevo`.

---

#### B. `views/usuario.templ` (y `views/usuario_templ.go`)

Contiene tres componentes:

1. **`ListaUsuarios(usuarios []db.Usuario, usuarioActivoID int32)`**
   - Es un **componente parcial** (no usa `LayoutBase`, porque se inserta dentro de `LayoutPrincipal`).
   - Si `len(usuarios) == 0`, muestra una tarjeta de estado vacío (`"No se han creado usuarios"`).
   - Si hay usuarios, recorre `usuarios` con un `for _, u := range usuarios` y genera una `<article class="user-card">` por cada uno:
     - Si `u.IDUsuario == usuarioActivoID`, le agrega la clase CSS `active` (usando `templ.KV("active", ...)`).
     - Muestra ID (`Usuario #id`), nombre, inicial del apellido, email y metadata.
     - Botón de acción:
       - Si coincide con `usuarioActivoID`: muestra un botón `"Sesión Activa"`.
       - Si no: muestra un enlace `"Iniciar Sesión"` hacia `/login?email=<email_del_usuario>`.

2. **`LoginPage(emailPrellenado string, errorMsg string)`**
   - Envuelve su contenido con `@LayoutBase("go_tasks - Iniciar Sesión", "")`.
   - Si `errorMsg != ""`, muestra un bloque `<div class="alert-error">` con el mensaje de error.
   - Renderiza un `<form action="/login" method="POST">` con dos campos:
     - `email` (prellenado con `emailPrellenado` si vino por query param desde la tarjeta de usuario).
     - `contrasena` (input tipo `password`).
   - Incluye un enlace abajo para volver a `/usuarios`.

3. **`TP6Aviso(usuarioNombre string)`**
   - Envuelve su contenido con `@LayoutBase("go_tasks - Próxima Entrega TP6", usuarioNombre)`.
   - Muestra una tarjeta avisando `"Esta funcionalidad se implementará en la próxima entrega TP6"` y un botón `"Volver a la página anterior"` con JS inline (`history.back()` o redirección a `/usuarios`).

---

#### C. `views/create_usuario.templ` (y `views/create_usuario_templ.go`)

Contiene un componente:

1. **`CreateUsuarioPage(errorMsg string)`**
   - Envuelve su contenido con `@LayoutBase("go_tasks - Crear Usuario", "")`.
   - Si `errorMsg != ""`, muestra un `<div class="alert-error">`.
   - Renderiza un `<form action="/usuarios" method="POST">` sin JavaScript (envío tradicional `application/x-www-form-urlencoded`) con 4 campos obligatorios:
     - `nombre`
     - `apellido`
     - `email`
     - `contrasena`
   - Tiene un botón **Cancelar** (enlace a `/usuarios`) y un botón submit **Guardar y Registrar Usuario**.

---

### 4. Flujo completo: Rutas (`main.go`) -> Handlers (`usuario_handler.go`) -> Vistas (`.templ`)

1. **`GET /{$}` o `GET /usuarios`** -> `handlers.UsuariosView`
   - Consulta `q.ListUsers(...)` en PostgreSQL.
   - Lee de la URL `?creado=ID` o `?activo=ID` para saber si debe marcar a algún usuario como activo.
   - Renderiza `views.LayoutPrincipal(...)`.

2. **`GET /usuarios/nuevo`** -> `handlers.CreateUsuarioView`
   - Renderiza `views.CreateUsuarioPage("")`.

3. **`POST /usuarios`** -> `handlers.CreateUsuario`
   - Si el `Content-Type` es `application/x-www-form-urlencoded` (viene del formulario HTML):
     - Valida campos vacíos; si falla o hay error de BD (ej. email duplicado), vuelve a renderizar `views.CreateUsuarioPage("mensaje de error")` directamente en la respuesta.
     - Si se crea bien en la BD, redirige (`303 See Other`) a `/usuarios?creado=<ID>`.
   - *(Si el `Content-Type` es JSON, responde JSON `201 Created` para la API REST/tests).*

4. **`GET /login`** -> `handlers.LoginView`
   - Lee `?email=...` de la URL y renderiza `views.LoginPage(email, "")`.

5. **`POST /login`** -> `handlers.LoginSubmit`
   - Busca el usuario con `q.GetUserByEmail` y compara `u.Contrasena != contrasena` en texto plano.
   - Si falla, vuelve a renderizar `views.LoginPage(email, "Contraseña incorrecta o usuario no encontrado")`.
   - Si es correcto, redirige (`303 See Other`) a `/tp6?nombre=<u.Nombre>`.

6. **`GET /tp6`, `GET /calendario`, `GET /materias`** -> `handlers.TP6View`
   - Lee `?nombre=...` (por defecto `"Usuario"`) y renderiza `views.TP6Aviso(nombre)`.

---

### 5. Detalles importantes a tener en cuenta antes de reformar

- **Pestaña activa fija en `LayoutBase`:** En `views/layout.templ`, el enlace `Usuarios` tiene la clase `active` hardcodeada (`class="nav-tab active"`). Si agregás vistas reales de Calendario o Materias, conviene pasar un parámetro `paginaActiva` a `LayoutBase` para resaltar la pestaña correcta.
- **Estado de sesión actual:** Hoy no hay cookies ni sesiones reales en el servidor; el "usuario activo" viaja por query params (`?creado=ID`, `?activo=ID`, `?nombre=...`).
- **Archivos estáticos vs Templ:** En `static/` todavía existen archivos `.html` (`index.html`, `usuarios.html`, `calendario.html`, `materias.html`), pero las rutas principales de `main.go` ya están usando las vistas `templ` y no esos HTML estáticos (solo se usan `./static/css` para los estilos).

# Cuando ingresás a `localhost:8080` en el navegador, si el handler de la página principal llama a `LayoutPrincipal`, ¿cómo y por qué se termina renderizando `LayoutBase`?

-- Aunque en `handlers/usuario_handler.go` el handler `UsuariosView` llama únicamente a `views.LayoutPrincipal(...)`, **`LayoutBase` se renderiza porque `LayoutPrincipal` lo invoca explícitamente por dentro** usando la sintaxis `@LayoutBase(...) { ... }` de Templ.

A continuación te muestro paso a paso qué ocurre desde que apretás Enter en `localhost:8080` hasta que el navegador recibe el HTML completo:

### 1. El navegador pide `GET /`
1. El navegador envía una petición HTTP `GET /` a `localhost:8080`.
2. En `main.go`, la ruta `http.HandleFunc("GET /{$}", ...)` captura exactamente la raíz `/` y ejecuta `handlers.UsuariosView(w, r, queries)`.
3. `UsuariosView` consulta los usuarios en PostgreSQL (`q.ListUsers(r.Context())`) y al final llama a:
   ```go
   views.LayoutPrincipal(usuarios, usuarioActivoID, usuarioActivoNombre).Render(r.Context(), w)
   ```

---

### 2. ¿Qué pasa dentro de `LayoutPrincipal`?
Si mirás `views/layout.templ` (líneas 85-107), `LayoutPrincipal` está escrito así:

```go
templ LayoutPrincipal(usuarios []db.Usuario, usuarioActivoID int32, usuarioActivoNombre string) {
	@LayoutBase("go_tasks - Gestión de Usuarios", usuarioActivoNombre) {
		<section class="page-header">...</section>
		@ListaUsuarios(usuarios, usuarioActivoID)
		<div class="user-actions-bottom">...</div>
	}
}
```

El símbolo **`@`** en Templ significa **"invocar otro componente Templ"**. Y las llaves `{ ... }` que le siguen le pasan un bloque de HTML/componentes como **hijos (`children`)**.

---

### 3. ¿Cómo lo resuelve el código Go generado (`views/layout_templ.go`)?
Cuando corrés `templ generate`, Templ transforma esa estructura en código Go real de esta manera:

1. **Empaqueta el contenido interno:** Todo lo que pusiste dentro de `@LayoutBase(...) { ... }` (el `<section class="page-header">`, la llamada a `ListaUsuarios(...)` y el botón de crear usuario) se guarda en una variable interna como un `templ.Component` hijo.
2. **Inyecta ese hijo en el `context.Context` y llama a `LayoutBase`:**
   ```go
   LayoutBase("go_tasks - Gestión de Usuarios", usuarioActivoNombre).Render(
       templ.WithChildren(ctx, componenteHijo),
       buffer,
   )
   ```
   Es decir, **`LayoutPrincipal` delega el renderizado a `LayoutBase`**, pasándole su propio contenido empaquetado dentro del `ctx`.

---

### 4. ¿Dónde se inserta el contenido dentro de `LayoutBase`?
Dentro de `LayoutBase` (`views/layout.templ`, líneas 14-73):
1. Primero escribe el `<!DOCTYPE html>`, el `<head>` (con fuentes, íconos y `/css/style.css`) y el `<header>` con la barra de navegación.
2. Abre `<main class="main-wrapper">`.
3. En la línea 69 aparece `{ children... }`. En ese punto exacto, `LayoutBase` extrae del `ctx` el `componenteHijo` que le envió `LayoutPrincipal` y ejecuta su `.Render(ctx, buffer)`:
   - Se dibuja el `<section class="page-header">`.
   - Se ejecuta `ListaUsuarios(...).Render(...)` (de `usuario.templ`).
   - Se dibuja el botón `"Crear Nuevo Usuario"`.
4. Finalmente, `LayoutBase` cierra `</main>`, `</body>` y `</html>`.

### Resumen visual del orden de ejecución
```text
GET / (localhost:8080)
 └─► handlers.UsuariosView
      └─► views.LayoutPrincipal.Render()
           ├─ empaqueta [Header sección + ListaUsuarios + Botón] como "children"
           └─► views.LayoutBase.Render(ctx con children)
                ├─ escribe <!DOCTYPE html>, <head>, <header> (navbar)
                ├─ abre <main class="main-wrapper">
                ├─ ejecuta { children... }  ──► escribe Header + ListaUsuarios + Botón
                └─ cierra </main></body></html>
```

Por eso, aunque el handler solo llame a `LayoutPrincipal`, el HTML que llega al navegador siempre tiene la estructura completa de `LayoutBase` envolviendo al contenido de `LayoutPrincipal`.
